# AI LEARNING SYSTEM: 쓸수록 나아지는 AI (Memory + Context Injection)

> 이 서비스에서 **"AI 학습"은 모델을 Fine-tuning하는 것이 아니다.**
> 사용자의 데이터를 **저장**해 두고, 생성할 때마다 **관련된 것만 골라 Context로 주입**하는 구조다.
> 코드: `lib/server/ai/context-builder.ts`, `lib/server/ai/prompts/*`, `lib/server/services/content-generation.ts`

---

## 1. 문제: AI 결과가 호출마다 달라지는 이유

| 원인 | 증상 | 이 시스템의 대응 |
|------|------|------------------|
| 정보 부족 | 제품 스펙을 모르니 일반론을 쓰거나 지어낸다 | **Product Memory**: 분석된 제품 정보를 항상 주입 |
| 취향을 모름 | 말투, 길이, 구조가 매번 다르다 | **Style Memory**: 채널 기본 스타일을 항상 주입 |
| 기준점 없음 | "좋은 결과"가 어떤 모습인지 모른다 | **Content History**: 사용자가 고른 좋은 예시를 few-shot으로 주입 |
| 같은 실수 반복 | 지난번에 싫다고 한 패턴이 또 나온다 | **Feedback Data**: "별로예요" 사유와 수정본을 금지 패턴으로 주입 |
| 성과를 모름 | 실제로 잘된 형식을 모른다 | **Performance Data**: 성과 상위 콘텐츠의 특징을 주입 |
| 프롬프트 흔들림 | 사람이 프롬프트를 매번 다르게 쓴다 | **고정 프롬프트 + 버전 관리**: 템플릿은 코드에 있고 버전이 붙는다 |
| 샘플링 무작위성 | 같은 입력에도 출력이 다르다 | 분석 작업은 낮은 temperature, 생성은 여러 후보(제목 5개)를 받아 사람이 고른다 |

## 2. 생성 파이프라인

```
고정 프롬프트 (system, 버전 관리)
  + 제품 데이터       (Product Memory)
  + 스타일 데이터     (Style Memory)
  + 과거 좋은 결과물  (Content History, isExemplar)
  + 피드백            (Feedback Data, rating=down)
  + 성과 데이터       (Performance Data)
  + 현재 트렌드       (선택한 TrendItem)
  + 사용자 입력
  + 출력 형식(JSON)
        ↓
     AIProvider.generateStructured()
        ↓
  정규화 + 정직성 검사
        ↓
  GeneratedContent 저장 (promptVersion, provider, model, contextSummary)
        ↓
  사용자 피드백 / 좋은 결과 저장 / 성과 수집 ──▶ 다음 생성의 Memory
```

**원칙: AI를 빈 Context로 호출하지 않는다.** 모든 생성은 `buildGenerationContext()`를 거친다.
비어 있는 Memory가 있으면 `contextSummary.notes`에 기록하고 화면("이번 생성에 사용된 학습 데이터")에 보여준다.
예: "기본 스타일 없음 → 나의 스타일에서 등록하면 결과가 일정해집니다."

## 3. 다섯 가지 Memory

### 3.1 Product Memory (제품별 고정 정보)
- **저장**: 제품 상세페이지 학습 → `ProductSource`(원문) + `ProductAnalysis`(구조화, version)
- **사용**: 생성 폼에서 제품을 고르면 `currentAnalysisId`의 분석 전체를 [제품 정보] 블록과 [사용 금지 표현] 블록으로 넣는다
- **재분석 금지**: 생성할 때마다 상세페이지를 다시 읽지 않는다 (비용, 속도, 일관성 모두 나빠진다). `lastUsedAt`만 갱신한다
- **갱신**: 사용자가 라이브러리에서 직접 고치거나(즉시 반영), 원문을 재분석해 version을 올린다
- **"사용하면 안 되는 표현"**: 과장 광고, 의료 효능, 허위 후기 위험 표현을 제품 단위로 금지한다

### 3.2 Style Memory (사용자 스타일)
- **저장**: AI 학습 관리 → 나의 스타일 (톤, 설명, 규칙, 자주 쓰는 표현, 금지 표현)
- **사용**: 채널 기본 스타일(채널당 1개) → 없으면 `all` 기본 스타일
- **팁**: 규칙은 측정할 수 있게 쓴다. "재밌게" 대신 "첫 문장은 질문형", "장점은 3개까지"

### 3.3 Content History (과거 생성 결과)
- **저장**: 모든 생성 결과를 `GeneratedContent`로 저장한다 (입력, 출력, 프롬프트 버전, 모델, Context 요약)
- **좋은 결과**: 결과 화면의 [좋은 결과로 저장] 또는 히스토리의 ★ → `isExemplar=true`
- **사용**: 같은 `featureId`의 좋은 결과 **최근 2건**을 [좋은 예시] 블록에 넣는다 (각 600자 이내로 자름)
  - 시스템 규칙: "예시는 톤과 구조만 참고하고 문장을 복사하지 않는다"

### 3.4 Feedback Data (좋아요 / 별로예요 / 수정본)
- **저장**: 결과 화면 하단 피드백 → `UserFeedback`
- **사용**: 같은 기능의 "별로예요" **최근 3건**의 사유와 수정본을 [피해야 할 패턴] 블록에 넣는다
- **수정본이 가장 강한 신호다**: "AI가 쓴 것 → 사용자가 고친 것" 쌍은 V2에서 스타일 자동 보정과 평가 데이터셋으로 쓴다
- 좋아요는 V1에서 통계로만 쓴다 (좋은 예시로 쓰려면 사용자가 명시적으로 "좋은 결과로 저장"을 눌러야 한다. 좋아요와 대표 예시는 다른 의미다)

### 3.5 Performance Data (성과)
- **저장**: `PerformanceMetric` (조회, 클릭, CTR, 좋아요, 댓글, 전환, 매출). V1은 Mock/수동 입력
- **사용**: 같은 채널에서 조회수 상위 **2건**을 [성과가 좋았던 콘텐츠]로 넣는다 (제목과 지표)
- **V2**: YouTube Analytics, 블로그 통계, 판매 데이터 연동. "좋은 예시"를 사람 선택 + 성과 상위 자동 선택으로 확장한다

## 4. RAG / Context Injection 방식

### 4.1 V1: 규칙 기반 선택 (현재 구현)
| Memory | 선택 규칙 | 상한 (`CONTEXT_LIMITS`) |
|--------|-----------|------------------------|
| Product | 사용자가 고른 제품 1개 | 1 |
| Style | 채널 기본 → all 기본 | 1 |
| Exemplars | 같은 기능 + isExemplar, 최신순 | 2 |
| Avoid | 같은 기능 + rating=down, 최신순 | 3 |
| Performance | 같은 채널 + 조회수 내림차순 | 2 |
| Trend | 사용자가 고른 것 | 1 |

데이터가 적을 때(수백 건 이하)는 규칙 기반이 예측 가능하고 디버깅이 쉬워서 RAG보다 낫다.

### 4.2 V2: 의미 검색 RAG (확장 지점)
- 좋은 결과물과 수정본을 임베딩해 `content_embeddings`(pgvector)에 저장한다
- 검색 쿼리는 현재 입력(주제, 키워드, 제품 카테고리)으로 만든다
- 점수 = 유사도 × (좋은 결과 가중치) × (성과 가중치) × (최신성 감쇠)
- `context-builder.ts`의 3)·5)번 단계만 바꾸면 된다. 프롬프트 블록 구조는 그대로다

### 4.3 토큰 예산
- 블록마다 상한을 두고(예시 600자 등) 전체 Context가 커지지 않게 한다
- 블록 순서: 작업 → 제품 → 금지 표현 → 스타일 → 예시 → 피드백 → 성과 → 트렌드 → 정직성 규칙 → 사용자 입력 → 출력 형식
- 바뀌지 않는 system 프롬프트를 맨 앞에 두면 Provider의 프롬프트 캐싱 효과를 받는다 (Claude는 `cache_control`, OpenAI는 자동 prefix 캐시)

## 5. Fine-tuning이 필요한 시점과 필요 없는 시점

| 상황 | 판단 | 이유 |
|------|------|------|
| 제품 정보, 최신 트렌드를 반영하고 싶다 | ❌ 불필요 | 자주 바뀌는 사실 정보는 Context Injection이 정확하고 즉시 반영된다 |
| 내 말투, 구조를 따르게 하고 싶다 | ❌ 대부분 불필요 | Style Memory + 좋은 예시 2~3개면 충분하다 |
| 금지 표현, 정직성 규칙 | ❌ 불필요 | 규칙은 프롬프트 + 생성 후 검사로 보장한다 (Fine-tuning은 규칙을 "확률적으로"만 학습한다) |
| 수정본이 기능당 수천 건 쌓였고, 프롬프트로 더는 개선되지 않는다 | ⭕ 검토 | 이때 비로소 데이터가 충분하다 |
| 매우 긴 Context 때문에 비용·지연이 문제다 | ⭕ 검토 | 스타일을 모델에 내재화해 프롬프트를 줄일 수 있다 |
| 특수한 출력 형식을 프롬프트로 안정화할 수 없다 | ⭕ 검토 | 단, 구조화 출력(JSON Schema)으로 먼저 해결을 시도한다 |

**순서**: 프롬프트 개선 → Memory 품질 개선 → 구조화 출력 → RAG → (그래도 안 되면) Fine-tuning.
Fine-tuning을 해도 Product/Trend Context 주입은 계속 필요하다.

## 6. 동일한 품질을 유지하는 방법 (체크리스트)

1. **고정 프롬프트**: 템플릿은 `lib/server/ai/prompts/templates.ts`에 있다. 화면에서 프롬프트를 자유 입력받지 않는다
2. **공통 규칙 단일화**: 모든 생성 템플릿이 `BASE_SYSTEM`을 공유한다 (사실 날조 금지, 금지 표현, 예시 복사 금지, JSON만 응답)
3. **구조화 출력**: Generator Config의 `outputs`로 JSON 형식을 지정하고, 서버에서 정규화한다 (list/tags는 배열, text는 문자열)
4. **결정적 Context**: 같은 입력이면 같은 Memory가 선택된다 (규칙 기반, 최신순)
5. **생성 후 검사**: 정직성 검사(`findHonestyViolations`) 결과를 `notes`에 경고로 남긴다. V2에서 금지 표현 전체 검사로 확장한다
6. **후보 여러 개**: 제목은 5개를 받아 사람이 고른다. 한 개만 받는 것보다 품질 체감이 안정적이다
7. **재현 정보 저장**: `promptId`, `promptVersion`, `provider`, `model`, `context`(무엇을 넣었는지)를 결과와 함께 저장한다
8. **모델 고정**: 모델명은 환경변수나 설정으로 고정한다. "최신 별칭"을 쓰면 결과가 몰래 바뀔 수 있다
9. **평가 세트**: (V2) 기능별 대표 입력 20~30개와 기대 기준을 만들어, 프롬프트를 바꿀 때마다 비교한다

## 7. Prompt Version 관리

```ts
// lib/server/ai/prompts/templates.ts
{
  id: "naver-blog.product-writing",
  version: "1.0.0",
  changelog: [{ version: "1.0.0", date: "2026-10-01", note: "최초 작성" }],
  system: BASE_SYSTEM,
  task: "...",
}
```

| 변경 | 버전 | 예 |
|------|------|----|
| 출력 구조(key) 변경 | MAJOR | `titles` 5개 → `titles` + `thumbnailTexts` 추가 |
| 지시 추가·변경, 블록 순서 변경 | MINOR | "소제목은 5개 내외" 추가 |
| 문구 수정, 오탈자 | PATCH | |

- 버전을 올리면 changelog에 **이유**를 쓴다
- 생성 결과에 버전이 저장되므로 "v1.1.0 이후 별로예요 비율"처럼 버전별 품질을 비교할 수 있다
- (V2) 템플릿을 DB로 옮기고 A/B 실험(사용자 일부에게 새 버전)을 한다. 그 전까지는 코드 리뷰로 변경을 관리한다

## 8. 생성 결과 Version 관리

| 개념 | 현재 | V2 |
|------|------|----|
| 결과 1건 | `GeneratedContent` (불변, 수정하지 않는다) | 같음 |
| 사용자 수정 | `UserFeedback.editedOutput` (원본은 보존) | 섹션별 편집기 → `content_revisions` 테이블 (rev 1, 2, …) |
| 같은 입력 재생성 | 새 `GeneratedContent` 생성 | `parentContentId`로 연결해 "재생성 이력"을 보여준다 |
| 묶음 | - | `ContentProject`로 제품·캠페인 단위로 묶는다 |

**원본 AI 결과는 덮어쓰지 않는다.** "AI 원본 ↔ 사람 수정본" 차이가 학습 데이터이기 때문이다.

## 9. 좋은 결과를 재사용하는 방법

1. 결과 화면에서 **[좋은 결과로 저장]** → 다음 생성부터 같은 기능의 [좋은 예시]로 들어간다
2. **AI 학습 관리 → 콘텐츠 히스토리**의 ★로 언제든 켜고 끈다 (나쁜 예시가 섞이면 바로 해제)
3. 성과가 좋은 콘텐츠는 V2에서 자동 후보가 되고, 사용자가 확정한다
4. 좋은 예시는 기능별로 따로 관리한다 (블로그 글 예시가 영상 대본에 섞이지 않게)
5. 예시는 너무 많이 넣지 않는다. 2~3개가 적당하고, 많으면 복사 경향과 비용이 늘어난다

## 10. 정직성 가드레일 (제품 콘텐츠)

- 제품 콘텐츠인데 **실제 경험** 입력이 비어 있으면 `honestyGuard=true`가 된다
- 프롬프트에 [정직성 규칙 (최우선)] 블록을 넣는다: 1인칭 사용 후기 표현 금지, 제품 정보 기반 소개 형식
- 생성 후 `FIRST_PERSON_EXPERIENCE_PHRASES`("써보니", "직접 사용해", "내돈내산" 등)를 검사해 경고를 남긴다
- 블로그 본문 첫 줄에 "※ 이 글은 제품 공식 정보와 공개된 스펙을 바탕으로 정리했습니다."를 넣는다
- 실제 경험을 입력하면 그 내용만 "직접 사용해 본 경험" 섹션에 쓴다 (경험을 부풀리지 않는다)

## 11. 다른 프로젝트에 재사용할 때

이 구조는 "사용자 데이터로 AI 출력을 개인화하는" 모든 서비스에 그대로 쓸 수 있다.

1. 도메인의 **고정 정보**(제품, 회사, 고객)를 구조화해 저장한다 → X Memory
2. 사용자의 **선호**(톤, 형식)를 저장한다 → Style Memory
3. **모든 생성 결과**를 입력, 출력, 버전, Context와 함께 저장한다 → History
4. **피드백과 수정본**을 받는다 → Feedback
5. **결과 지표**를 연결한다 → Performance
6. 생성 요청마다 `ContextBuilder`가 위 데이터를 골라 **버전 관리되는 프롬프트 템플릿**에 주입한다
7. 무엇을 주입했는지 결과와 함께 저장하고 화면에 보여준다 (신뢰와 디버깅)
