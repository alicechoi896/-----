# INCREMENTAL_LEARNING — 쓸수록 맞춰지는 생성 (학습 프로필)

> v0.9.18 (2026-10-03). 코드: `lib/server/services/learning.ts`, `lib/learning-config.ts`, `lib/server/ai/context-builder.ts`
> 화면: AI 학습 관리 › 학습 프로필, 생성 결과의 [직접 수정]·후보 체크

## 1. 개념 — Fine-tuning 이 아니다

| | Fine-tuning | 이 서비스 (Incremental Learning) |
|---|---|---|
| 무엇을 바꾸나 | 모델 가중치 | 생성 때 함께 보내는 작은 요약(학습 프로필) |
| 비용·시간 | 학습 비용, 수 시간, 데이터 수백~수천 건 | 신호 10개마다 AI 1회 (약 40~50원) |
| 모델 교체 | 다시 학습 | 그대로 (Claude/OpenAI 어느 쪽이든 같은 요약을 받는다) |
| 되돌리기 | 어려움 | 직전 버전 1개 보관 → 관리자가 되돌리기 |

```
생성 → 피드백·직접 수정·선택·업로드 완료·성과 (학습 신호)
     → 새 신호 10개 → AI 1회: 기존 프로필 + 새 신호 요약 → 새 프로필 (작은 Insight 목록, v+1)
     → 다음 생성: 학습 프로필 + 좋은 예시 요약만 참고
```

과거 데이터가 10개든 10,000개든 생성 때 보내는 양은 거의 같다.

## 2. 학습 프로필 (learning_profiles) — 팀 공통

- 채널·유형별 1행, **최대 6행** (서비스 전체)
  - YouTube 제품 / 정보성, NAVER 클립 제품 / 정보성, NAVER 블로그 제품 / 정보·자동 (자동 글쓰기는 정보글과 합친다)
- `summary_json`: 8개 항목 × 최대 10개 Insight — 제목, Hook, 구조, CTA, 키워드, 좋은 특징, 피해야 할 특징, 표현 조정
- Insight: `{ text, support_count, positive_count, negative_count, confidence, last_seen_at }`
- `previous_summary_json`: 직전 버전 1개 (되돌리기). 전체 버전 기록은 저장하지 않는다
- `user_cursors`: 사용자별 마지막 반영 시각. 공통 프로필이지만 각자 **자기 콘텐츠만** 읽을 수 있어서(RLS) 업데이트는 "그 사람의 새 신호"로 공통 프로필을 고친다
- 원문은 복사하지 않는다. 한 행 약 1~6KB
- 권한: 승인된 직원 조회·학습 반영, 삭제는 관리자, 되돌리기는 관리자 (서비스)

## 3. 학습 신호 (Qualified Learning Signal)

신호가 있는 콘텐츠만 학습한다 (테스트로 만들고 안 쓴 결과는 학습하지 않는다).

| 신호 | 출처 | 강도 |
|---|---|---|
| 직접 수정 | 결과 [직접 수정] → `context.userEdits` (원본은 output 에 그대로, 수정량 ratio) | 가장 강함. 수정량이 적을수록 원래 결과가 잘 맞았다는 뜻 |
| 선택한 후보 | 제목·Hook·CTA 후보 체크 → `context.picks` | 강함 ("어떤 제목을 썼는지" 힌트) |
| 👍 / ★ / 업로드 완료 | user_feedback / is_exemplar / content_publications(published) | 긍정 |
| 👎 + 사유 | user_feedback | 부정 → 피해야 할 특징 |
| 성과 | performance_metrics | 참고 (한 콘텐츠의 수치로 강한 결론 금지) |

[다시 만들기](대본·설명글·본문)를 하면 그 항목의 수정·선택 기록은 지운다 (새 결과에는 맞지 않으므로). 후보 목록의 [추가 만들기](v0.9.22)는 새 후보를 위에 더할 뿐이라 수정본·체크한 후보를 그대로 둔다.

## 4. 업데이트 (Threshold · Incremental)

- `learningConfig.updateThreshold = 10`: 내 새 신호가 10개 쌓이면 자동 (응답을 보낸 뒤 `after()` 로 실행 → 생성·저장이 느려지지 않는다)
- [지금 학습 업데이트]: 기준 전에도 수동으로 (새 신호 1개 이상)
- 입력: 기존 프로필 JSON + **마지막 반영 이후** 신호가 있는 콘텐츠 최대 15개의 요약본
  - 영상: 제목(쓴 제목 우선)·Hook·대본 흐름(앞 6줄)·CTA
  - 블로그: 제목·도입부 180자·소제목·마무리
  - 수정본이 있으면 수정본 기준
- 출력: 엄격한 JSON Schema. 서버가 다시 정리한다: 80자 제한, 중복 병합, 근거 1개면 confidence ≤ 0.4, 항목당 10개, 최근성 가중치로 정렬
- 다른 팀원이 동시에 업데이트했으면(버전이 바뀌었으면) 이번 것은 버리고 다음에 다시 (덮어쓰기 방지)
- 실패: `last_error` 에만 남기고 기존 프로필로 계속 생성

## 5. 생성 때 사용 (Context Compression)

- 학습 프로필: 근거 2개 이상 · confidence 0.35 이상인 Insight 만, 신뢰도×최근성 순, **최대 1,500자**
- 프롬프트: "[학습 프로필 vN — 팀이 실제로 써 보며 발견한 경향 (참고용)] 규칙·금지 표현·나의 스타일이 우선한다. 모든 결과에 똑같이 적용하지 말고 다양성을 유지한다"
- 우선순위: **규칙·금지 표현 > 나의 스타일 > 학습 프로필 > 트렌드**. 학습 프로필이 나의 스타일을 고치지 않는다
- 좋은 예시: 긍정 결과(★·👍·업로드 완료·선택·거의 안 고친 수정) 무작위 3 + 일반 1, 최근 10번 생성에 쓴 예시는 확률 0.3배, 각 450자 요약
- 기록: `context.learningProfile {id, version, insightCount}`, `context.goodExampleIds`

## 6. 크기 관리

| | 크기 |
|---|---|
| DB | 프로필 6행 × 1~6KB. 생성 기록 context +약 200B (수정본이 있으면 그만큼) |
| 생성 Payload | 학습 프로필 ≤1,500자 + 예시 4개 × ≤450자 (기존 ★ 예시 2개 × 600자 대체) → 약 +2,000자 고정 |
| 학습 Payload | 기존 프로필 ≤6,000자 + 요약 15개 → 입력 약 4천 토큰, 출력 ≤3천 토큰 |

## 7. 추적 · 측정

생성 기록마다 학습 프로필 버전이 남으므로, 새 테이블 없이 기존 데이터로 버전별 👍 비율·👎 비율·수정량(userEdits.ratio)·업로드율을 계산할 수 있다 (NEXT_STEPS).

## 8. 장애 시

학습 프로필이 없거나 읽기·업데이트가 실패해도 생성은 그대로 된다 (학습 없이 나의 스타일·제품·트렌드로 생성).

## 9. 향후 Fine-tuning 검토 기준

- 한 채널·유형에서 직접 수정·선택 신호가 수천 건 이상 쌓이고
- 학습 프로필 버전이 올라가도 👍 비율·수정량이 더 좋아지지 않을 때
- 그리고 모델 교체 비용을 감수할 만큼 일관된 형식이 필요할 때
